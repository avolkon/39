## 2. Высокий потенциал улучшения (по приоритету)

### 2.1. Использовать связь `SI ≈ CC50 / IC50` (кросс-таргет)

**Наблюдение:** три таргета обучаются **независимо** (`train.py` цикл по `TARGETS`), ансамбль — взвешенное среднее по имени модели (`ensemble.py`). На train в EDA тождество `SI ≡ CC50/IC50`; на платформе связь нужно **явно верифицировать**.

**Что добавить без тяжёлой переделки:**

- После \(\widehat{IC50},\widehat{CC50}\) считать \(\widetilde{SI} = f(\widehat{CC50}, \widehat{IC50})\) и либо отдавать как SI, либо обучать **небольшой остаток** к `SI` (регрессия ошибки доли относительно \(\widetilde{SI}\)).  
**Риск:** другая дефиниция SI на тесте — слейка ухудшит RMSE; нужен офлайн-абляционный эксперимент.

### 2.2. Ансамбль второго уровня (stacking / blending по OOF)

**Сейчас:** веса из **обратного среднего RMSE по моделям** на том же ClusterKFold, затем фиксируются и применяются к финальным моделям.

**Ограничение одного уровня:** линейная комбинация по фиксированным каналам не извлекает «когда модель A лучше B» по областям признаков.

**Улучшение:** сохранять **внефоловые (OOF)** предсказания каждого базового алгоритма по всем объектам train, затем метамодель (ridge / маленький LGBM), строго **без утекания** val в train меты. Инкремент на табличных соревнованиях часто скромный, но **устойчивый**.

### 2.3. Системный подбор гиперпараметров

**Сейчас:** `utils/config.py` содержит `use_optuna: bool`, но **`train.py` флаг не читает**; `hyperopt.py` ограничен `run_optuna_stub()` — полноценного objective нет.

**Улучшение:** Optuna или хотя бы **random/grid** по топ-семействам (`lgb`, `xgb`, при наличии `catboost`), **пер-модельно** по каждому таргету, с тем же ClusterKFold. Это главный контролируемый рычаг после архитектурных упрощений.

### 2.4. Дубликаты и группы объектов в CV

**Риск:** `ClusterKFold` не гарантирует, что строки с **идентичным признаковым вектором** но **разными** `IC50`/`CC50` не попадут вместе в train и val через «случайный» порядок внутри одного фолда. В EDA дубликаты ~16%.  

**Улучшение:** групповой split по **ключу признаков** или по кластерам-дубликатам (`GroupKFold`/аналог или эвристика «одна представительная строка на группу» при согласованности таргетов — см. также `docs/eda/Аналитическая_записка_архитектура_моделей.md`, §5).

### 2.5. Совместная оптимизация метрики соревнования

**Сейчас:** веса подбираются **пер таргет** по RMSE этого таргета; итоговый скор платформы — **среднее RMSE по трём столбцам** (`metrics.competition_score` описывает именно это, но пайплайн обучения не минимизирует это среднее **напрямую как scalar loss** за один шаг).

**Улучшение:** при подборе весов/blending использовать **единый scalar** \(\frac{1}{3}(\mathrm{RMSE}_{IC50}+\mathrm{RMSE}_{CC50}+\mathrm{RMSE}_{SI})\) по OOF-тензору прогнозов (дороже по коду, зато выровняно под лидерборд).

## 3. Средний потенциал

### 3.1. SI: шкала и робастность

Использование `log1p` только для IC50/CC50 (`train.py`, `cfg.log_transform_ic50_cc50`). Для SI — сырая шкала; при толстых хвостах полезно пробовать **`log1p(SI)`**, Huber к выбросам **как эксперимент**, с пониманием, что платформа считает RMSE в тех же единицах, что файл сабмита.

### 3.2. Препроцессор: более агрессивный фильтр для линейных моделей

`preprocessor.py` отбрасывает колонки с долей пропусков выше порога и **нулевой дисперсией после заполнения**. Для блока деревьев польза вторична; для Ridge/Elastic — иногда имеет смысл **немного более жёсткий** порог дисперсии для стабильности коэффициентов при небольшом \(n\).

### 3.3. Постобработка `postprocess.py`

Клипинг `IC50`/`CC50` с пола `1e-8`, `SI >= 0` — биологический здравый смысл **может расходиться** с платформенным округлением или с тем, мог бы ли быть отрицательный SI в данных конкурса. Имеет смысл один раз замерить **RMSE без постобработки** как абляцию на локальном hold-out.

### 3.4. Доп. признаки из таблицы

`features/build_features.py` добавляет узкий набор отношений и флагов поверх уже богатых столбцов. Без SMILES можно аккуратно добавлять **ограниченное** число взаимодействий по топ-дисперсии или важности деревьев, чтобы не раздуть размерность на \(n\approx750\).

## 4. Низкий ROI при текущих данных и конфигурации

| Тема | Почему |
|------|--------|
| GNN и тяжёлая NN | Нет смолструктуры в репозитории; конфиг **`use_neural_net` не пробрасывается в `train_pipeline`** — путь только через явное расширение кода при большой цене экспериментов. |
| Новые fingerprints (Morgan и т.д.) | Нужны SMILES/InChI или внешний справочник; в выданных данных только числовые дескрипторы. |
| Полный CatBoost без extras | Полезный кандидат уже предусмотрен при `pip install catboost`. |

## 5. «Мёртвые» конфиги (техдолг, не всегда влияние на качество)

- **`use_neural_net`:** задаётся в `Config`, но **не используется** в коде обучения (поиск только в `config.py`).
- **`use_optuna`:** аналогично до появления реального цикла в `train_pipeline`; сейас — `run_optuna_stub()` в `hyperopt.py`.

**Итог:** возможность качественного улучшения есть; **первая волна** — связь **SI**, **stacking**, **тупящий моделей через Optuna/поиск** и **защита CV от дубликатов**.
